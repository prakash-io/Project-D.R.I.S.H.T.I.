# D.R.I.S.H.T.I. — Driver Client (Epic 4)

React Native app with a C++ edge engine. Streams GNSS at 1 Hz when online;
when the valley takes both the satellites and the network, dead-reckons from
the IMU and snaps to the offline road graph until signal returns.

## Layout

```
native/         the engine — no React Native in it, testable on a laptop
  Geo.h                 lat/lon <-> local ENU metres
  IMU_Constants.h       GENERATED by scripts/gen_model_header.py
  DeadReckoning.{h,cpp} decimator + Eigen EKF (MOB-04)
  MapMatcher.{h,cpp}    SQLite R*Tree lookup + projection (MOB-06)
  EdgeEngineApi.{h,cpp} one flat C surface for both platforms
  EKF_TFLite_Bridge.cpp TFLite speed inference (MOB-05 consumer)
  test/                 79 checks, run with make
android/ ios/   thin JNI and Objective-C++ marshalling over EdgeEngineApi
src/            WatermelonDB queue, tracking mode switch, Burst Sync, TTS
```

## Verify the engine

```bash
make -C mobile-app/native/test run      # 79 checks
make -C mobile-app/native/test strict   # full warning set
```

No NDK, emulator or device needed: the tests link against the real
`road_graph.sqlite` and a stubbed TFLite, so the parts most likely to be wrong
are checkable in a second.

## Five things that will bite you

**The model is 10 Hz; the handset is 100 Hz.** IO-VNBD was logged at 10 Hz, so
a 50-step window is 5 seconds. Feeding 100 Hz samples straight in makes every
window cover 0.5 s and the model sees a distribution it never trained on — and
still returns a confident number. `ImuDecimator` averages 10 raw samples into
one. Averaging, not sub-sampling: at 100 Hz the accelerometer carries engine
and road vibration well above 5 Hz, and taking every tenth sample aliases it
straight into the band the model reads.

**Heading is a compass bearing.** Clockwise from North, so velocity is
`(v sin h, v cos h)` and *not* `(v cos h, v sin h)`. Getting it backwards
gives a track that is a perfect mirror of the truth — plausible on a map right
up until it isn't. Asserted in the tests both ways.

**The speed model is a weak measurement, by construction.** R = its own
held-out RMSE² = 27.66 (m/s)², and the seed prior is 1.0 m²/s² because a GNSS
speed is good to well under 1 m/s. Seeding the prior with the *model's*
variance instead makes the Kalman gain 0.5 — measured: a 0.0 m/s reading
dragged 20 m/s down to 9.96. With the correct prior it moves to 19.14.

**Map matching is what actually bounds the drift.** Unaided, 60 s of dead
reckoning leaves a position variance of ~262,000 m². With a snap every 5 s it
is 14.4 m². The speed model alone cannot hold a truck on the map.

**A road has a bearing but no direction.** Snapping to a northbound
carriageway while driving south must not spin the estimate 180°. The heading
update picks whichever of the two orientations is nearer the current heading.

## Status

The C++ engine is complete and verified. The React Native layer is
**scaffolded, not built**: there is no Android/iOS toolchain in this
environment, so `npm install`, Gradle and CocoaPods have not been run and the
app has never launched on a device or emulator. The JS parses and the native
shims are written against the same C API the tests exercise, but treat the RN
layer as reviewed source, not as a running app.
